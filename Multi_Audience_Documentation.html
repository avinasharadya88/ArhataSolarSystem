What is this thing?

No jargon. Promise.

🛒 Imagine you bought the wrong-sized shoes online

You ordered shoes. The website said size 5. But when they arrived, they were way too small. So you had to send them back. That's called a return.

Now imagine this happening to millions of people every day. The shoe company has to ship the shoes back, inspect them, and figure out what to do next. That costs a LOT of money.

🤔 Why did this happen?

The website's description was wrong or confusing. Maybe the size chart was missing. Maybe the photo showed something different from the real product. The listing — what the website says about the product — had a mistake in it.

The problem this app solves

📢 Nobody was listening to customers

When lots of people returned the same shoes saying "runs too small," that information was sitting in a computer somewhere — but nobody was connecting it to the listing that caused the problem.

This app listens to those complaints automatically, figures out what the listing got wrong, and suggests a fix. Then it creates a task for the team to go fix it.

What happens after a fix?

STEP 1

📝 Fix the description

The size chart gets corrected. Fewer people buy the wrong size. Fewer returns.

STEP 2

🔄 Offer an exchange

Instead of giving money back, the store says: "Want to swap for the right size? We'll give you a little bonus!" Many people say yes.

STEP 3

🎁 Keep it free

If shipping the item back costs more than the item is worth, the store just says: "Keep it, here's part of your money back." Saves everyone trouble.

STEP 4

♻️ Resell it

For items that do come back, the app helps sort them out and sell them again at a discount — instead of throwing them away.

💡
The big idea: Instead of just losing money on every return, this app tries to save some of that money at every step.

How does the computer do it?

🤖 The app reads customer complaints

When someone returns something, they often write a reason. The app reads thousands of these reasons really fast, spots patterns ("size issue" keeps coming up for these shoes), and figures out exactly what needs to change on the website.

Then it automatically makes a little task — like a sticky note — for a real person at the company to review and approve the fix.

Who built this?

👨‍💻 It's a real app on the internet

This app was built using a coding language called React (for the dashboard you see on screen) and Python (for the behind-the-scenes computer work). All the code is saved on a website called GitHub, where coders share their work.

Returns are bleeding e-commerce companies dry — this is the fix

Think business problem meets AI solution.

🏪 The e-commerce returns problem

Online stores like Amazon, Flipkart, and Shopify deal with massive return rates — sometimes 20–30% of all orders. Every return costs money: shipping the item back, inspecting it, restocking it, or just writing it off.

The wildest part? Most of those returns happen because the product listing — the title, description, photos, and size charts on the website — gave customers the wrong information.

Why doesn't anyone just fix the listing?

📂 The data is trapped in the wrong place

Customer return reasons, reviews, and complaints live in one software system. The product catalog — what's actually shown on the website — lives in another. Nobody was automatically connecting these two.

Category managers (the people responsible for a product group) spent hours manually reading through spreadsheets trying to spot patterns. Meanwhile, the bad listing kept causing more returns.

What this app does about it

1

Listens to return signals in real time

When a customer returns an item, the system automatically receives a notification (called a webhook) with the return reason.

2

AI figures out what went wrong

Using an AI technique called zero-shot classification, the app reads the return reason and buckets it: "sizing issue," "misleading photo," "wrong material description," etc. — without needing to be trained on thousands of examples first.

3

Drafts the fix and assigns a task

The app generates an exact suggestion for what to change in the listing, then creates a work ticket in tools like Jira or Linear — the task management software engineering teams use.

4

Shows the financial impact

The dashboard has an interactive calculator where you can slide around assumptions — "what if we prevent 25% of returns?" — and see the real dollar impact on the business.

The 4 profit levers

LEVER 1

Fix the listing, prevent the return

Better size charts, accurate material specs, correct photos. Prevents 18–30% of returns before they happen.

LEVER 2

Swap refund for exchange

Offer the customer a +10% store credit bonus to exchange instead of refund. Store keeps the money in the system.

LEVER 3

"Keep it" micro-refund

If returning a $15 item costs $12 in shipping, just give the customer a partial refund and let them keep it. Net saving: ~$11.

LEVER 4

Grade and resell returned units

Automatically sort returned items and sell them as "certified open box" at 58% recovery instead of bulk liquidation at 15%.

Closing the loop between customer friction signals and catalog quality

A practical AI-powered system for a real, expensive business problem.

The disconnect that costs billions

E-commerce return rates typically run 20–30%, with fashion hitting 40%+. The bulk of these are preventable: customers buying a product that the listing misrepresented — a size chart that hasn't been updated, a fabric description that doesn't match reality, photos that show a different color under studio lighting.

The problem isn't that companies don't have the data. They have mountains of it: return reason codes, 1–3 star reviews, customer service transcripts, Q&A threads. The problem is that this data lives in customer support tools (Zendesk, Intercom) and reverse-logistics systems, completely disconnected from the catalog management workflow.

The bottleneck: manual signal processing

Category managers as the chokepoint

In most organizations, a category manager manually reads through support exports, tries to spot patterns, writes up findings, creates tickets, and then follows up with copywriters. At scale, this fails. The lag between a return signal appearing and a listing getting fixed can be weeks or months — during which the same bad listing keeps generating more returns.

This system replaces that manual loop with an automated pipeline: return webhook → AI classification → listing fix draft → ticket auto-created in Linear or Jira.

The financial model: 4 levers from loss to profit

Traditional returns accounting treats them as a straight write-off: outbound shipping + reverse logistics + inspection labor + inventory depreciation. The system models four intervention points instead.

LEVER 1 · PREVENTION

Catalog fixes reduce return volume

Zero-shot extraction of sizing, material, and assembly gaps auto-patches the listing. Target: 18–30% reduction in preventable returns.

LEVER 2 · RETENTION

Exchange-over-refund incentives

A +10% bonus store credit offer converts refund requests into exchanges. Gross margin is retained. Customer LTV is preserved rather than paid out as cash.

LEVER 3 · ARBITRAGE

Keep-it micro-refund

Where shipping ($7.50) + handling ($4.50) exceeds a low-value item's salvage, a 60% partial refund eliminates $11+ in net logistics cost.

LEVER 4 · RECOVERY

Automated grading + recommerce

Returned inventory routed to certified open-box channels at ~58% salvage vs. the ~15% bulk liquidation rate.

The AI classification system

Zero-shot classification for root cause tagging

Return text is fed to an LLM with a structured prompt that asks it to classify into one of five root causes without any fine-tuning on labeled examples:

  • Sizing / Fit Discrepancy — P1 priority
  • Material Quality Drift — P2
  • Misleading Listing Image — P2
  • Missing Assembly / Dimension Spec — P3
  • Pricing & Promotion Drift — P3

The model also outputs a confidence score and the specific listing field that needs updating, along with a copy-pasteable suggested fix.

Domain context first

E-commerce platforms deal with product return rates of 20–40%. Most of these returns are triggered by listing quality issues — wrong size charts, inaccurate material descriptions, misleading photos. The data proving this exists in return reason codes, reviews, and support transcripts, but nobody was programmatically connecting it to catalog updates.

This system is a full-stack prototype that closes that loop: ingest return signals, classify root cause via LLM, generate remediation copy, and dispatch a structured issue to Linear or Jira.

Webhook ingestion details

FastAPI backend (backend_server.py)

POST endpoint accepts return payloads from upstream systems (Zendesk webhooks, marketplace APIs). HMAC-SHA256 validation uses hmac.compare_digest for timing-safe comparison to block replay attacks. The endpoint returns 200 OK immediately and kicks off the classification pipeline asynchronously to meet the <5s SLA.

The repo also ships a simulate webhook trigger in the UI — a built-in generator that injects realistic return payloads with mock HMAC signatures for development and demo purposes.

LLM classification prompt design

Zero-shot classification with structured output. The prompt passes customer return text and asks the model to output one of five categories, a confidence score, the affected listing field, and a copy fix suggestion. No fine-tuning required — works on raw unstructured text from any source.

// Classification schema (simplified) { category: "SIZING_FIT" | "MATERIAL_QUALITY" | "MISLEADING_IMAGE" | "ASSEMBLY_SPEC" | "PRICING_DRIFT", priority: "P1" | "P2" | "P3", listing_field: "size_chart" | "material_description" | "images" | "dimensions" | "pricing", confidence: 0.0 – 1.0, proposed_copy_fix: "..." }

Issue dispatch: Linear and Jira

Linear GraphQL

Endpoint: POST https://api.linear.app/graphql. Auth: Authorization: lin_api_... — no Bearer prefix. Mutation: issueCreate with a structured Markdown body containing SKU, category, customer quote, proposed fix, and priority.

Jira Cloud REST v3

Endpoint: POST /rest/api/3/issue. Body formatted using Atlassian Document Format (ADF) — a nested JSON schema Jira requires for rich-text fields. Not plain text.

Frontend architecture

React + TypeScript + Vite

The UI has several distinct modules:

Testing setup

Decoupled QA agent architecture

Testing is intentionally decoupled from the main development agent. A dedicated qa_test_agent subagent handles: financial formula verification, edge case coverage, zero-shot classification precision testing, and API payload schema validation. Vitest is the test runner.

Run with npm run test. The QA agent operates independently to avoid context pollution in the main development workflow.

The AI classification system in detail

Zero-shot root cause taxonomy

Five categories, prioritized by return-rate impact and fix complexity:

  • P1 — Sizing / Fit Discrepancy: Highest volume, most directly addressable via size chart updates. Immediate listing change, measurable return rate impact within 14–21 days.
  • P2 — Material Quality Drift: Fabric GSM changes from supplier without listing updates. Requires supplier coordination + listing copy fix.
  • P2 — Misleading Listing Image: Studio lighting color shifts, angle misrepresentation. Requires photography workflow fix upstream.
  • P3 — Missing Assembly / Dimension Spec: Most common in furniture, electronics accessories, flat-pack. One-time fix with high durability.
  • P3 — Pricing & Promotion Drift: Expectation mismatch from expired promotions still indexed in search results.

Each classification includes a confidence score and a specific listing field reference — not just a category label. The proposed fix is copy-pasteable into the listing editor directly.
